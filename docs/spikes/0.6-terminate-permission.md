# Spike 0.6 — `NSRunningApplication.terminate()` and TCC permissions

**Date:** 2026-10-19 · **macOS:** 27.0.1 (build 26A434) · **Target app:** TextEdit (`com.apple.TextEdit`) only

## Verdict

**No TCC permission is needed to gracefully quit another regular app with `NSRunningApplication.terminate()`, and no prompt is shown.** The call returned `true`, TextEdit received a normal Quit Apple Event, approved termination and exited in ~50 ms. This held for:

- a plain CLI binary run from a terminal/agent host (responsible process = the host app, which is hardened-runtime and has no Automation entitlement);
- a minimal ad-hoc-signed `.app` bundle (no hardened runtime);
- a minimal ad-hoc-signed `.app` bundle with hardened runtime (`-o runtime`) and no entitlements.

`AXIsProcessTrusted()` was `false` throughout, so Accessibility is **not** required. No Automation (`kTCCServiceAppleEvents`) grant exists for any of the test identities and none was requested/denied.

`NSWorkspace.openApplication(at:configuration:)` with `activates = false`, `hides = true`, `createsNewApplicationInstance = false` also needs no permission and behaved as intended (details below). `forceTerminate()` was **not** called (info only; see notes).

One nuance: the public consent probe `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)` returns `-1744` (`errAEEventWouldRequireUserConsent`) for `aevt/quit` from our app, even though `terminate()` succeeds. So `terminate()` is **not** equivalent to "my app sends a quit Apple Event to X" for consent purposes. Do not replace it with a hand-built Apple Event / `NSAppleScript` / `tell application … to quit` — that path would require Automation consent.

## Safety / state

- TextEdit was **not running** before every run (`pgrep -x TextEdit` and `NSRunningApplication.runningApplications(withBundleIdentifier:)` both empty). Each program re-checked and would have aborted otherwise.
- No documents created/edited, no save sheet appeared, no permission prompt appeared, no `forceTerminate`, no `killall`, no other app or the Dock touched.
- After the last run `pgrep -x TextEdit` → empty. **TextEdit ended in the same state it started (not running).**
- All test code lived in `mktemp -d` (not in the repo). The consent probes use `askUserIfNeeded: false`, which cannot show UI.

## Apple docs: what mechanism does `terminate()` use?

`NSRunningApplication.h` (macOS 27 SDK): *"Attempts to quit the receiver normally. @return YES if the request was successfully sent, NO if not (for example, if the application is no longer running). This method may return before the receiver exits; you should observe the terminated property or listen for the notification to detect when the app has exited."* `forceTerminate()` is identical wording for a forced quit.

- Mechanism: the log shows `spike → appleeventsd` and TextEdit logging `Handling Quit AppleEvent` → `applicationShouldTerminate:` → `terminate:`. So it **does** deliver a standard Quit Apple Event (`aevt/quit`) via the system AE service — i.e. it is subject to the app's normal quit handling (save sheets, `applicationShouldTerminate:` returning `.terminateCancel`/`.terminateLater`, etc.).
- It is evidently **not** treated as an app-to-app Automation send: `AEDeterminePermissionToAutomateTarget(aevt/quit, ask:false)` says `-1744` for our process yet `terminate()` succeeds with no consent. (`AppleEvents.h` documents that "Certain AppleEvents are allowed to be sent without prompting the user" but does not list them; `NSRunningApplication` is documented only as returning whether the request was sent.)
- Automation / `NSAppleEventsUsageDescription` is only required if the app sends **its own** Apple Events to another app (AppleScript, `NSAppleScript`, `SBApplication`, `NSAppleEventDescriptor.send`, `osascript`). That is *not* the `terminate()` path. It would become relevant only if the AppSwitcher later adds scripted features (e.g. asking Finder/Terminal for state, `tell app … to quit` to work around apps that ignore the AE, closing documents). Not needed for this spike's scope.
- No documented Accessibility requirement: `AXIsProcessTrusted()` was false and quit worked.

## CLI-vs-app caveat

TCC attributes requests to the *responsible process* (the app that spawned the chain): for the CLI run that was the terminal/agent host (T3 Code, hardened runtime, **no** `com.apple.security.automation.apple-events` entitlement; tccd's "responsible=" field shows exactly that). So a CLI result could differ from an app because (a) a pre-existing Automation grant on the host could mask a requirement, (b) the identity that would appear in System Settings → Privacy → Automation is the host, not our binary.

Why the result transfers to a real bundle:

1. **Test 2 removed the host as the actor.** `open` launches the `.app` via launchd/LaunchServices, so the app is its own responsible process; tccd logged `dev.spike.terminate06` as the accessing identity. Same outcome with and without hardened runtime.
2. The one thing that could mask a missing requirement — a previously granted Automation entry — cannot apply to `dev.spike.terminate06` (brand-new identity, never granted) nor to the unentitled hardened host in Test 1 (a hardened process lacking the entitlement can't even be *prompted* for Automation: the tccd log line says so, yet the quit worked). Together, this indicates no Automation grant was involved.

What would differ for the shipped app (Developer ID, hardened runtime, notarized, non-sandboxed):

- **Signing identity:** TCC keys on the designated requirement. Real Developer ID identity → stable across updates, unlike ad-hoc (cdhash-based, changes per build). Not relevant for terminate (no grant needed), but relevant to any future Automation grant.
- **Hardened runtime + Apple Events:** with hardened runtime on, sending Apple Events requires `com.apple.security.automation.apple-events` plus `NSAppleEventsUsageDescription`, otherwise the OS silently denies instead of prompting (this is exactly the tccd "Prompting policy for hardened runtime" message). Irrelevant to `terminate()` per the tests, relevant only for scripted AE sends.
- **Not sandboxed** (per project): sandbox would add `com.apple.security.temporary-exception.apple-events` considerations; N/A here.
- **Untested here:** real notarized Developer ID build; a macOS where the user has MDM/PPPC profiles restricting Apple Events; quitting apps that show a save sheet / `applicationShouldTerminate` veto (needs a TextEdit document — explicitly out of scope).

## `openApplication` flag behavior observed

TextEdit (not running beforehand), `activates=false`, `hides=true`, `createsNewApplicationInstance=false`:

| Observation | CLI | App 2a | App 2b |
|---|---|---|---|
| Completion handler fires | 0.327 s | 0.156 s | 0.153 s |
| `err` | nil | nil | nil |
| `activationPolicy` | 0 (regular) | 0 | 0 |
| `isHidden` at callback | **false** | false | false |
| `isActive` at callback | false | false | false |
| `isFinishedLaunching` at callback | false → true after 0.454 s | → true 0.104 s | → true 0.052 s |
| After 1 s settle: `isHidden` | **true** | true | true |
| After 1 s settle: `isActive` | false | false | false |
| Frontmost app unchanged | yes (T3 Code) | yes | yes (com.todesktop.230313mzl4w4u92) |

Takeaways:

- `activates=false` works: the launched app never became active and the previously frontmost app stayed frontmost.
- `hides=true` works **asynchronously**: `isHidden` is still `false` in the completion handler and flips to `true` within the next second. Do not read `isHidden` right in the callback; observe via KVO (`isHidden` is KVO-compliant) or re-check after `isFinishedLaunching`.
- `isFinishedLaunching` is `false` in the callback — poll/KVO it before interacting with the app.
- The completion handler's `NSRunningApplication` is `@Sendable` / main-run-loop-bound: its time-varying properties only update when the main run loop runs, so the CLI had to pump `RunLoop.current` (a bare `sleep` would never see changes). The AppSwitcher runs on the main actor with a live run loop, so this is fine.
- No window ever required interaction in these runs; I did not observe an open panel or new-document window blocking quit (and did not inspect windows since the app stayed hidden).

## Recommendation for the AppSwitcher

1. **Do not add `NSAppleEventsUsageDescription`, and do not add `com.apple.security.automation.apple-events`**, for the quit/launch features. Quitting via `NSRunningApplication.terminate()` and launching via `NSWorkspace.openApplication` need neither. Adding the usage string would only create user-visible consent surface (and possible prompts) without benefit. Add them later only if a feature sends its own Apple Events.
2. **No first-use permission flow is needed** for quit/launch. No Accessibility prompt, no Automation prompt. Do **not** gate the switcher UI on `AXIsProcessTrusted()`.
3. Use `terminate()` only; avoid hand-rolled Apple Events / AppleScript quit — those *do* hit the consent path (`-1744` probe).
4. Treat `terminate()` as **request, not guarantee**: returns `true` when the request was delivered; completion is asynchronous. Await `isTerminated` (KVO) with a timeout (~10 s was ample; TextEdit quit in ~50 ms). Apps with unsaved docs or `applicationShouldTerminate` veto will stay running — surface "still running / didn't quit" in the UI and let the user decide (offer force-quit explicitly, never automatically; not tested here).
5. Launch with `NSWorkspace.OpenConfiguration`: `activates = false`, `hides = true` works; wait for `isFinishedLaunching` via KVO rather than trusting state in the completion handler; handle `err != nil` (missing bundle, etc.).
6. Optional hardening: before the first real profile switch, re-run this spike on a Developer ID–signed, notarized build (and one machine with PPPC/MDM) to confirm no policy-dependent difference; keep the spike's probe code (`AEDeterminePermissionToAutomateTarget(ask:false)`) around as a non-prompting diagnostic if scripting features are added later.

## Notes

- `forceTerminate()` was intentionally not called. Header says it behaves like `terminate()` (returns whether the request was sent; may return before exit) but forces; nothing more tested.
- Environment quirk: in zsh `timeout` doesn't exist and `log` is a builtin; use `/usr/bin/log` for unified logging.
- Temp artifacts (binaries, bundles, logs) live under `mktemp -d` outside the repo and were not committed.
